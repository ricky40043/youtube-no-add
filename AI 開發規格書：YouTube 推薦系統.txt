第三方 YouTube 推薦系統架構與實作規範技術報告
1. 執行摘要與系統概述
本研究報告旨在針對擁有「播放清單、訂閱、觀看紀錄」自有資料庫的第三方平台，提出一套完整的 YouTube 推薦演算法實作邏輯與開發規範。鑑於 YouTube 原生演算法的封閉性及其優化目標（主要為廣告收益與平台留存率）可能與使用者個人的特定需求（如學習效率、資訊密度掌控）存在偏差，第三方平台的價值在於構建一個「透明化」、「可解釋」且「高度客製化」的推薦引擎。
本報告首先深入解構 Google 團隊（Covington 等人）發表的深度神經網路（DNN）推薦架構，剖析其「候選集生成（Candidate Generation）」與「排序（Ranking）」的雙塔機制。隨後，針對 2026 年 YouTube Data API v3 的技術現況，特別是 relatedToVideoId 與 activities.list (home) 等關鍵端點的棄用，提出替代的數據獲取策略。核心技術方案聚焦於建立一個「混合過濾（Hybrid Filtering）」系統，該系統結合基於內容的過濾（Content-Based Filtering, CBF）與基於協同過濾（Collaborative Filtering, CF）的特徵，利用 Jaccard 相似度計算語義關聯，並引入指數時間衰減（Exponential Time Decay）函數來模擬內容的新鮮度偏好。
報告最終章節將轉化為具體的工程指令，提供資料庫架構設計（SQL Schema）、API 串接邏輯、分頁游標策略（Cursor-based Pagination）及演算法權重公式，旨在直接指導人工智慧（AI）工程師進行程式碼開發，實現一個具備工業級效能與精準度的第三方推薦系統。
2. YouTube 原生推薦演算法之解構分析
要構建一個能與 YouTube 原生體驗媲美甚至互補的推薦系統，首要任務是理解其背後的運作邏輯。根據 Covington 等人於 Google Research 發表的經典論文《Deep Neural Networks for YouTube Recommendations》1，YouTube 的推薦系統並非單一模型，而是一個由多個神經網路組成的複雜漏斗（Funnel）架構。
2.1 雙塔架構：從海量到精準
YouTube 面臨的核心挑戰在於「規模（Scale）」。在擁有數十億影片的語料庫（Corpus）中，即時為使用者計算每一部影片的評分在算力上是不可行的。因此，系統被設計為兩個主要階段：候選集生成（Candidate Generation）與排序（Ranking）。
2.1.1 第一階段：候選集生成（Candidate Generation）
此階段的目標是「高召回率（High Recall）」。系統需要從數十億的影片中篩選出數百部（例如 500 部）與使用者「廣義相關」的影片 2。
分類問題的定義： 模型將推薦問題視為一個超大規模的多類別分類問題（Extreme Multiclass Classification）。其數學目標是預測在時間 ，使用者  在上下文  下觀看影片  的機率：

特徵輸入： 模型的輸入包括使用者的觀看歷史（Watch History）、搜尋歷史（Search History）以及人口統計學特徵（如地理位置、性別、登入設備）。
近似最近鄰搜索（ANN）： 為了加速檢索，YouTube 使用近似最近鄰搜索演算法。使用者的歷史行為被映射為一個高維向量，系統在向量空間中尋找與該使用者向量最接近的影片向量群 4。
協同過濾的本質： 此階段本質上是一種非線性的廣義協同過濾。它不依賴於影片的具體內容（如像素或音頻分析），而是依賴於「群體行為」——即類似的使用者看了什麼。
2.1.2 第二階段：排序（Ranking）
此階段的目標是「高精確度（High Precision）」。系統接收來自候選集生成的數百部影片，並對其進行精細評分，決定最終在使用者介面上呈現的順序 1。
目標函數的轉變： 與傳統廣告系統優化點擊率（CTR）不同，YouTube 的排序網路優化的是預期觀看時間（Expected Watch Time）。這是為了防止「點擊誘餌（Clickbait）」——即標題聳動但內容空洞導致使用者快速跳出的影片。
特徵工程的細緻化： 排序模型使用更豐富的特徵，包括：
上下文特徵： 當前的時間、星期幾、網路連線狀態。
互動特徵： 使用者過去是否觀看過該頻道的影片？上次觀看是什麼時候？
印象數據（Impression Data）： 該影片是否曾經推薦給使用者但未被點擊？（這是一個強烈的負面訊號）4。
加權邏輯回歸： 模型通常使用加權邏輯回歸（Weighted Logistic Regression），其中正樣本（被觀看的影片）的權重是其觀看時長。這樣，模型的輸出分數就直接對應於預期的觀看分鐘數。
2.2 新鮮度（Freshness）與時間偏差
YouTube 演算法的一個顯著特徵是對「新鮮內容」的強烈偏好。使用者傾向於觀看最新發布的影片，即使這些影片的相關性略低於某些經典舊片。
模型機制： 為了捕捉這種非平穩（Non-stationary）的數據分佈，YouTube 將「影片上傳後經過的時間（Time Since Upload）」作為一個顯著特徵輸入給模型。
結果： 模型會學習到一個偏差：在其他條件相同的情況下，發布時間越短的影片得分越高。這對於新聞、科技評論或娛樂趨勢類內容尤為重要 2。
2.3 第三方平台的模仿策略
對於第三方平台而言，由於無法存取 YouTube 內部的全量使用者行為數據（即無法訓練全網級別的協同過濾模型），我們必須採取**「基於內容的混合過濾」**策略。我們擁有使用者的「訂閱列表」和「觀看紀錄」，這足以構建一個局部的、以使用者為中心的候選集生成器，並利用 API 獲取的元數據（Metadata）進行排序。
3. 資料獲取層：API v3 技術規格與限制分析 (2025-2026)
在規劃開發步驟前，必須明確 YouTube Data API v3 在 2026 年的可用性與限制。過去幾年間，Google 對 API 進行了多次重大調整，移除了多個便於構建第三方客戶端的功能。
3.1 關鍵端點棄用與影響評估
3.1.1 relatedToVideoId 的移除
在 2023 年 8 月之前，開發者可以透過 search.list 端點並帶上 relatedToVideoId 參數，直接獲取 YouTube 原生的「相關影片」推薦列表。此功能已被正式棄用 7。
技術影響： 第三方平台無法再「代理」YouTube 的推薦結果。我們必須自行實作推薦邏輯，無法依賴 YouTube 的黑盒輸出來填充「接下來播放」清單。
3.1.2 activities.list (home=true) 的失效
早期 API 允許透過 activities.list 配合 home=true 參數來獲取使用者的個人化首頁動態。此功能亦已被棄用，目前調用會返回 403 Forbidden 或 404 Not Found 10。
技術影響： 我們無法直接讀取使用者的「首頁」。必須透過聚合使用者訂閱頻道的「上傳（Uploads）」內容來合成一個自定義的首頁動態牆（Feed）。

3.3 資料獲取策略：上傳清單聚合（The Uploads Playlist Strategy）
由於無法直接查詢「某頻道的所有影片」，最高效的方法是利用每個頻道隱藏的「上傳清單」14。
獲取上傳清單 ID： 調用 channels.list，請求 contentDetails 部分。回應中的 contentDetails.relatedPlaylists.uploads 欄位即為該頻道所有上傳影片的播放清單 ID（通常將頻道 ID 的 UC 前綴改為 UU 即可，但透過 API 獲取更穩健）。
輪詢上傳清單： 使用 playlistItems.list 查詢該 ID，即可按時間倒序獲得該頻道的最新影片。此操作僅消耗 1 單位配額。

6. Feed 聚合與分頁策略：統一游標 (Unified Cursor)
當系統從 100 個不同的頻道聚合內容時，如何實現高效的「無限捲動（Infinite Scroll）」是一個巨大的技術挑戰。傳統的 OFFSET 分頁在數據量大時效能極差，且在動態 Feed 中會導致數據重複或遺漏 22。

Task: 構建推薦 Feed API。
Requirements:
端點：GET /api/v1/feed?cursor=...&limit=20
候選集檢索： 從 videos 表中選取該使用者訂閱頻道的影片（限制過去 30 天內發布）。
即時評分： 將檢索到的影片傳入 RecommendationScorer 進行評分。
排序與切片： 根據分數降序排列。
游標處理：
若無 cursor，返回 Top 20。
若有 cursor (解碼為 last_score, last_id)，過濾掉分數高於 last_score 的項目，從中取 Top 20。
回應格式： 返回 JSON，包含影片列表與 next_cursor。
8. 結論與未來展望
本報告提出了一種繞過 YouTube API 限制、構建自主推薦系統的完整技術路徑。透過將「候選集生成」從伺服器端（依賴 search.list）轉移到客戶端資料庫（依賴 subscriptions + playlistItems），我們不僅解決了配額瓶頸，更將推薦演算法的控制權交還給使用者。
此架構的核心價值在於其透明性與可調性。使用者不再是被動接收黑箱演算法的餵食，而是可以透過調整 （相關性）與 （新鮮度）參數，主動決定他們想要探索新知還是追蹤時事。這種「Glass Box（玻璃箱）」推薦系統代表了下一代內容聚合平台的發展方向，既利用了 YouTube 龐大的內容生態，又規避了其演算法對使用者注意力的過度掠奪。
8.1 開發檢核清單 (Checklist)
為了確保專案順利執行，開發團隊應遵循以下檢核點：
[ ] Schema 驗證： 確認 videos 表的 tags 欄位設為 JSONB 並建立 GIN 索引。
[ ] 配額監控： 實作 API 請求計數器，當接近 10,000 單位時自動降級同步頻率。
[ ] 冷啟動處理： 確認當使用者無觀看紀錄時，系統能自動降級為純時間排序（Reverse Chronological）。
[ ] 隱私合規： 確保 watch_history 的存儲符合當地資料隱私法規（如 GDPR），並提供使用者「一鍵清除紀錄」功能。
